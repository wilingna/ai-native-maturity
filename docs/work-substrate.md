# 第 0 问：你的组织，工作到底发生在哪里？

> **Work Substrate — 定位题，不打分。**
> 在测六个维度之前，先回答这一题。它不决定你的水位，但决定你**该把 AI 放在哪**。
> 答错这一题，六个维度做得再对，落地也会水土不服。

---

## 为什么要问这一题

几乎所有主流的 AI 落地方法论，都有一个没被说出口的默认前提：

> **工作发生在群聊里。**

所以它们的建议长这样：把 agent 拉进团队频道、让它在讨论里自动响应、把它当成"群里的一个同事"。这些建议在硅谷是对的——那里的组织，讨论、决策、交接、文档链接，确实都在 Slack 里发生。群聊就是工作本身。

**但这是一个文化前提，不是普遍规律。**

把同样的建议搬到一家大型制造企业、一家国企、一家有严格层级的传统公司，往往会失败。不是因为方法不对，是因为**那里的工作根本不在群聊里发生**。群里只有全员通知和新人自我介绍。真正的工作发生在会议室、在邮件、在文档、在一对一汇报里。

把 agent 装进一个没人干活的群，等于把它装在没人经过的地方。

> 2026 年的研究也在印证这一点：**组织因素对 AI 成效的影响，约是个人因素的两倍**。
> 工具和个人技能当然重要，但"工作在哪发生、怎么被组织起来"才是更大的变量。

## 四种工作基质

大多数组织以其中一种为主，另有一到两种为辅。

### A. IM 基质（群聊型）
**特征**：讨论、决策、交接都在群聊里发生；群聊有完整上下文；@ 某人是有效的工作指派。
**常见于**：互联网公司、创业公司、外企的技术团队。
**agent 该嵌在哪**：群聊。可 @ 唤起，进度在同一个帖子里可见。
**这是绝大多数西方方法论的默认前提。**

### B. 会议基质（会议型）
**特征**：真正的决策发生在会上；会前准备材料、会中讨论、会后跟进；不开会就推不动。
**常见于**：大型制造企业、国企、有强层级的传统组织。
**agent 该嵌在哪**：会议。会前自动备料、会中实时检索与投屏、会末生成待办并当场确认。
**关键动作**：把 agent 投在屏幕上当众使用，而不是发一个工具链接让大家自己试。

### C. 文档基质（文档型）
**特征**：决策沉淀在文档里；文档评审是主要协作方式；重要的事都要"落个文"。
**常见于**：研发密集型组织、咨询公司、部分远程公司。
**agent 该嵌在哪**：文档编辑器与评审流。起草、批注、按规范检查、版本比对。

### D. 系统基质（流程型）
**特征**：工作以工单/表单/审批流为载体；人在系统里推进任务；离开系统就没有工作记录。
**常见于**：运营密集型组织、服务型企业、有成熟 ERP/OA 的公司。
**agent 该嵌在哪**：业务系统本身。在工单流转的节点上自动处理、预填、校验。

## 怎么判断自己是哪一种

不要问"我们用什么工具"，问这三个问题：

1. **上周最重要的那个决定，是在哪里做出的？** ——会上？群里？某份文档的评论区？还是某个审批流里？
2. **如果要找回三个月前某件事的来龙去脉，你会去翻什么？** ——聊天记录、会议纪要、文档版本，还是系统日志？
3. **新人要搞清楚一件事在怎么推进，你会让他去哪儿看？**

三个问题指向同一个地方的，那就是你的主基质。指向不一致，说明组织内部基质分裂——这时候**按部门分别判断**，不要强行给全公司一个答案。

## 这一题的三个用法

### 用法一：决定 agent 的落点
基质在哪，agent 就该嵌在哪。**agent 要长在工作真实发生的地方**——这句话是通用的，但"哪里"因组织而异。

### 用法二：决定"观摩"怎么做
让人看着 agent 干活，是采纳最快的推广方式——人不因为"更有效率"而采纳新技术，人因为**看见相似的人用它并拿到好结果**而采纳。经理当众用 AI 的团队，成员对 agent 的信任度明显更高。

但"观摩现场"在哪，取决于基质：

| 基质 | 观摩现场 |
|---|---|
| IM | agent 在群里干活，全员可见 |
| **会议** | **投屏当众使用，不预演、不挑好用的场景** |
| 文档 | agent 的批注和修改痕迹留在文档里 |
| 系统 | 处理记录在工单流水上人人可查 |

会议型组织尤其要注意：**让大家看到它有时也答不好、你怎么调整、然后它答对了**。"翻车—修正—成功"的过程，比一次完美演示的说服力大得多——完美演示传递的是"这东西很神但只有专家能玩"，真实使用传递的是"这东西我也能用"。

### 用法三：识别"水土不服"的根因
如果你的组织**六个维度分数不低，但落地就是推不动**，先回来检查这一题。很可能你把 agent 装在了一个正确但空无一人的地方。

## 一个反面案例

某企业推 AI 助手，选择部署在企业 IM 上，理由是"员工都有账号"。上线三个月，日活个位数。

复盘发现：这家公司的 IM 只用于发通知，员工每天打开它不超过两次，且从不在里面讨论工作。真正的协作发生在每周十几场会议里。**工具没问题，模型没问题，位置错了。**

后来改为在会议中投屏使用、并在会末自动生成待办，很快成了部门标配。

**同一个 agent，同一个模型，换了个位置，结果完全不同。**

## 一个容易踩的坑：在公开大群里放"答疑 agent"

会议型组织常有一个折中想法：既然没有工作群，那就在全员大群里放一个 @ 就能答疑的 agent（比如 HR 问答）。

**建议缓一缓。** 两个原因：

1. **它不产生观摩效应。** 员工问、bot 答，大家看到的是一个 FAQ 工具，不是"一个同事在干活"。
2. **风险不对称。** 在全员群里，员工最想问的往往是薪酬、晋升、调整这类敏感问题；**公开场合的每一个回答都可被截图转发**。

更稳的做法：答疑类 agent 放在内部平台里**一对一**提供。私密、可控、出错影响面小——而且留下的提问日志，本身就是一份"员工真实需求图谱"。

## 与六个维度的关系

工作基质**不打分**，它是前置定位，不进最短板计算。一家会议文化的企业不比 Slack 文化的企业"低级"，只是 agent 该嵌的位置不同。

但它会影响你在两个维度上的动作设计：

- **场景与流程（03）**：AI 该嵌进的"那条流程"，其载体由基质决定。
- **人才与能力（04）**：让人学会用 AI 的场合，由基质决定。

**先答第 0 问，再测六个维度。**
